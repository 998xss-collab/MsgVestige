# 快速开始

> 这份文档里的每一条命令和每一段输出, 都是在真机上真跑出来的, 不是照帮助文本编的。
> 照着敲就能通;敲不通的地方, 底下「卡住了怎么办」有对应条目。

---

## 这是什么

一个**读你自己电脑上微信数据**的命令行工具。

- **只读**。它不改微信的任何东西, 跑完你的微信照旧。
  这不是靠「我们小心不写」保证的, 是**写不进去**, 而且是三层各自独立地写不进去:
  ① 微信的库文件是用**只读的文件句柄**打开的 —— 操作系统这一层就不允许写;
  ② 上面那层是自己实现的只读存储层, 任何写/截断/删除请求直接返回 `SQLITE_READONLY`;
  ③ 已解密的明文库另走 SQLite 的 `READ_ONLY` 标志。
  它写文件只写这几个地方: 自己的缓存/日志目录、`%TEMP%`(底下有表 —— 多数是小文件,
  但 `watch` 会在这里建**很大的**临时库)、你指定的库、你指定的导出目录,
  以及 `logs bundle` 把诊断包落在你当前所在的目录。**微信的文件一个都不碰。**
- **不上传任何数据**。会**主动往外连**的只有这几处, 而且全是**下载**:
  `decrypt-emoji`(表情包不存在本地, 只能按记录里的地址去微信 CDN 下)、
  `export-sns-media`(朋友圈图片视频同理)、
  以及 `serve` 的媒体接口被请求表情/朋友圈图时(同样是去 CDN 取)。
  `serve` 本身只在**本机**监听(默认 127.0.0.1, 别人连不上)。除这几处全程不碰网络。
- **在你自己机器上跑**。数据不出本机。
- **不是双击就能用的窗口程序**,是命令行工具 —— 要在终端里敲命令。

能拿到哪些数据(消息、联系人、群、朋友圈、收藏、转账红包……), 看解压目录里的 `数据可见性矩阵.md` ——
那里逐类写了「能不能拿到 / 从哪条路拿 / 拿不到卡在哪」, 每一格都是真库跑出来的。

## 开始之前

| 需要 | 说明 |
|---|---|
| Windows 10(1809 或更新)/ Windows 11,64 位 | 32 位系统跑不了 |
| 微信 4.0 以上, **已登录过、收发过消息** | 实测 4.0.3.x / 4.1.11.24 都能跑。没有本地数据就查不到东西 |
| 一个终端 | Windows Terminal / PowerShell / cmd 都行 |
| 硬盘空间 | 看你的数据量。**只导小表**实测出来 1.1 GB;**连聊天记录一起导**能到几十 GB |
| 内存 | 不高。只导小表实测**峰值约 450 MB**(两次测得 424 / 450)。导聊天记录没测, 会更高但不是量级差别 |

**不需要**装运行库(VC++ 那些)、不需要装 Python。解压就能用。
有两处例外, 都在**完整版**包里备齐了。

**一是导朋友圈图片视频**(`export-sns-media`, 以及 `serve` 取加密朋友圈图时),
它要 Node 和一个 wasm 文件 —— **完整版包里都带了, 不用你装**。
**精简版做不了这一件事**: 光装 Node 不够, 还得从源仓库取 `vendor/weflow_wasm/` 放到 exe 同级。
要用就直接下完整版。

**二是语音导成 mp3、以及少数图片的格式转换**, 要 ffmpeg —— 完整版带了(195 MB, 精简版
故意不带就是为了这个体积)。精简版遇到这两件事: 语音会导成 wav(照样能听), 那几张图片留原格式。

除这两件, 其余功能精简版全都能用。
(程序是静态链的, 实测两个 exe 的依赖全是 Windows 自带的系统 DLL, 没有一个外部 DLL。)

## 先跑一下体检(可选, 但建议)

```
.\msgvestige.exe doctor
```

一次看清环境缺什么。**微信数据不在默认位置的话会看到一个 🛑**(默认位置是 `我的文档\xwechat_files`),
别慌, 下面就是解法。这是数据在 F: 盘时的真实输出:

```
msgvestige doctor — 环境自检
  ✅ 平台           Windows x64
  🛑 微信数据目录       没探测到 xwechat_files — 用 --wechat-data-dir 指定
  ⚠️ wx_key.dll   没找到 — 不影响默认路径 (auth --scan 走纯 Rust 内存扫, 不需要它) …
  ⚠️ key 缓存       未给 --wxid, 跳过 (给 --wxid <你的 wxid> 可查 key 是否已缓存)
  ✅ 临时目录可写       C:\Users\…\Temp\
  ⚠️ ffmpeg       未找到 (语音转 mp3 / 图片 wxgf 转码不可用; 装 ffmpeg 或设 WECHAT_FFMPEG, 可选)

结果: 2 通过 / 3 警告 / 1 失败 → 环境未就绪 (先修 🛑 项)
```

**🛑 那条要处理**: 它默认只找 `我的文档\xwechat_files`, 你的微信数据在别的盘就探测不到。
把两个参数补上再跑一次:

```
.\msgvestige.exe doctor --wechat-data-dir "X:\xwechat_files" --wxid wxid_你的号
```

补上之后(同一台机器, 只是加了参数), 🛑 变成 ✅, **这就算环境就绪了**:

```
  ✅ 微信数据目录       X:\xwechat_files (检测到 3 个账号)
  ⚠️ key 缓存       wxid_你的号 未缓存 — 跑 `msgvestige auth --wxid wxid_你的号` 取一次

结果: 3 通过 / 3 警告 / 0 失败 → 环境就绪
```

「key 缓存」这时候还是 ⚠️ **正常** —— 你还没跑第一步呢。跑完第一步再来看就是:

```
  ✅ key 缓存       wxid_你的号 的 key 已缓存

结果: 4 通过 / 2 警告 / 0 失败 → 环境就绪
```

> ⚠️ 注意它提示的是 `auth --wxid …`, **没有 `--scan`**。照抄会走杀微信重登那条路,
> 下面第一步会讲。

**剩下的 ⚠️ 不用管**, 精简包本来就不带那两样:
- `wx_key.dll` —— 只有不带 `--scan` 的那条回退路要它, 默认路径不需要。
- `ffmpeg` —— 只影响语音导成 mp3(不带就导 wav)和图片 wxgf 转码。
  **完整版包里带了, 会自动找到**(那条会显示 ✅); 精简版看到这条 ⚠️ 是正常的。

**退出码**: 有 🛑 是 1, 没 🛑 是 0(⚠️ 不影响)—— 想写脚本判断的话用这个。

## 三步走

下面用 `wx.db` 当你的数据库文件名, 放哪儿都行。

> **每条命令开头都会打一行这个**, 是正常的日志提示, 不用管, 下面的输出示例里都省掉了:
> ```
> INFO common::log: 日志系统就绪 (终端 + 按天文件, 留 14 天) log_dir=…\msgvestige\logs
> ```

### 第一步:取密钥

微信的数据是加密的, 得先把密钥取出来。

```
.\msgvestige.exe auth --scan
```

`--scan` 是**不打扰**的方式:从正在运行的微信进程内存里读, **不杀微信、不重启、不用重新扫码**。
所以跑之前**微信要开着并且已登录**。

跑通长这样:

```
非扰动内存扫 full 路 (Weixin.dll 提 internal_db_key → 扫裸 key 候选 XOR 反混淆 → PBKDF2-256000; 不杀 / 不重启微信)…
✅ 已扫到并缓存 wxid#a1b2c3d4 的 key (非扰动 full 路, 全程未动微信; sha8=f0e1d2c3)
```

上面第一行看不懂没关系, 那是它在报告用了哪条路 —— **只要最后有 ✅ 就行**。
密钥会缓存起来, 以后不用重复取。

> ⚠️ **跳过这一步直接跑第二步的话**, 它会提示你「先跑 `msgvestige auth --wxid <你的 wxid>`」——
> 那句话里**没有 `--scan`**。照抄会走另一条路: **杀掉微信重启、让你重新扫码登录**。
> 想省事就照本节这样带上 `--scan`。

**如果报错**, 多半是下面两种, 底下都有解法:
- `没找到微信数据目录` → 加 `--wechat-data-dir`
- `检测到 N 个账号` → 加 `--wxid`

### 第二步:建库

把微信的数据解密、整理成一个你自己的数据库文件。

```
.\msgvestige.exe ingest --no-messages --all --l1-db wx.db --wxid wxid_你的号
```

> ⚠️ **第一步用到的参数, 这一步要再带一遍。**
> `--wxid` 是**必填**的 —— 不带直接报 `the following required arguments were not provided: --wxid`。
> 第一步如果还加了 `--wechat-data-dir`, 这一步**也要加**, 否则报「没找到微信数据目录」。
> 密钥是缓存下来了, 但「去哪个目录、读哪个号」每条命令都要各自说清楚。
>
> 数据目录不在默认位置时的完整形态:
> ```
> .\msgvestige.exe ingest --no-messages --all --l1-db wx.db --wxid wxid_你的号 --wechat-data-dir "X:\xwechat_files"
> ```

`--no-messages` 是**先不导聊天记录**,只导联系人、群、会话、朋友圈这些小表。
**强烈建议第一次这么跑** —— 几分钟就好, 能马上看到东西; 而导聊天记录动辄几小时。

跑完会把 18 类逐一报数, 这是一次真实的完整输出:

```
✅ ingest 完成 (18 类落库):
  contact: 落库 51910 条
  chatroom: 落库 群 1599 个 · 成员 +69739
  session: 落库 15540 条
  favorite: 落库 154 条
  favorite_tag: 落库 6 条

  group_pay: 落库 11 条
  friend_verify: 落库 8143 条
  finder_visit: 落库 779 条

```

认得出的几类: 联系人 5.2 万、群 1599 个(成员 7 万)、会话 1.5 万、朋友圈 1.3 万、
转账 2298 笔、红包 680 个、好友申请 8143 条。

剩下的: `moment_feed` 朋友圈原始时间线、`avatar_image` 头像、
`sns_notify` 朋友圈通知、`custom_emoticon` 自定义表情、`stranger` 陌生人、
`finder_visit` 视频号足迹、`biz_message` 公众号推送。
(最后这个说明 `--no-messages` 跳过的是**聊天**记录, 公众号推送仍会导 —— 它不占大头。)

> **`moment_feed` 那个数要单独说一句**: 它是**写入次数**, 不是表里的行数。上面报 426785,
> 而表里实际 334086 行(差 28%)—— 因为同一条动态会被重复投递、写多次。
> 其余 16 类的数字都精确等于表里的行数, **只有这一类不是**。别拿它当"你有 42 万条朋友圈"。

真机实测: **3 到 4 分钟**(同账号同参数跑了四次: 206 / 215 / 233 / 254 秒), 出来一个 **1.1 GB** 的 `wx.db`。
(同机同参数波动这么大是正常的 —— 取决于盘忙不忙。)

聊天记录要另外导 —— 见底下「导聊天记录」。

### 第三步:查

> 下面这些输出**是真跑出来的**, 只是把里面的标识打了码 —— 群号中间几位、微信号中间几段、
> 群名、消息正文、账号指纹、翻页游标都换掉了, **格式、字段、条数一个没动**。
> 你跑出来的人名、群名、条数当然跟这里不一样, 只要**格式长得一样**就是对的。

```
.\msgvestige.exe sessions --l1-db wx.db --mode cold -n 3
```

```
会话 15540 个 (取前 3):
群    5795****030@chatroom [未读1]  [内容已打码]
群    4497****364@chatroom  
群    4303****671@chatroom  你撤回了一条消息
```

```
.\msgvestige.exe contacts --l1-db wx.db --mode cold -n 3
```

```
联系人 (本页 3 个, 还有下页):
某某人才求职  [1072****502@chatroom]  
某某代理群2✅  [1240****857@chatroom]  
某某兼职招聘信息平台  [1554***153@chatroom]  
下一页: --cursor Y3Vyc29yLXNhbXBsZS1yZWRhY3RlZC1zZWUtcmVhbC1vdXRwdXQ
```

**翻页**: 把那行 `--cursor xxx` 原样接在命令后面就是下一页。
(报错里管它叫「**游标**」, 就是这个东西。)

> ⚠️ **想把结果存成文件的注意**: 数据行走标准输出, 而**表头和那行 `下一页: --cursor …`
> 走标准错误**。所以 `contacts … > out.txt` 存下来的文件里**没有 cursor**, 翻页信息会丢。
> 要连提示一起存: `contacts … > out.txt 2>&1`(注意两个流合并后顺序可能交错)。

> 查询这一步**不需要** `--wxid` 和 `--wechat-data-dir` —— 数据已经在你的 `wx.db` 里了,
> 不用再碰微信。
> 只有前两步(取密钥、建库)才要那两个参数。

到这儿就跑通了。

## 两个参数, 记住就够用

这两个几乎每条查询命令都要带:

**`--l1-db wx.db`** —— 告诉它查哪个库。不带的话它会去读实时的微信库(那需要另外的参数),
所以查自己建好的库时**一定要带**。

> `L1` 就是这个工具给自己那个库起的名字, 没别的意思 —— 你会在参数名和报错里反复看到它。
> 报错里还会出现「**冷查**」和「**热查**」——
> 冷查 = `--mode cold`(查你的库), 热查 = `--mode hot`(直接读实时微信库)。

**`--mode cold`** —— 明确告诉它「查我建好的那个库」。

**这个要带, 不能省。** 因为各命令的默认值不一样(实测):

| 命令 | 不写 `--mode` 的默认 | 只给 `--l1-db` 够不够 |
|---|---|---|
| `sessions` / `messages` | **`hot`** 实时读微信库 | **不够, 会报错** |
| 其余全部 | `auto` 给了库就查库 | 够 |

「其余全部」指 `contacts` `search` `moments` `money` `export`
`chatrooms` `locations` `links` `files` 等。
实测 38 个带 `--mode` 的命令里, 只有 `sessions` 和 `messages` 默认是 hot。

也就是说, `sessions --l1-db wx.db -n 3` 这样敲会失败:

```json
{ "_error": "BAD_REQUEST",
  "_hint": "实时查 (--mode=hot, 或 auto 无 --l1-db) 需 --wxid; 要冷查改 --mode=cold --l1-db <L1 库>" }
```

**记不住就一律带 `--mode cold`** —— 对上面所有命令都是对的, 不会错。

三个值的含义: `cold` 查你的库 · `hot` 直接读实时微信库(要 `--wxid`) · `auto` 看给没给 `--l1-db` 定。

## 导聊天记录

第二步故意跳过了聊天记录。要导的话把 `--no-messages` 去掉:

```
.\msgvestige.exe ingest --all --l1-db wx.db --wxid wxid_你的号
```

(同样, 数据目录不在默认位置的话再加 `--wechat-data-dir`。)

**会很久** —— 消息量大的账号几小时, 库能到几十 GB。建议:
- 后台跑, 别等着

> **中途断了怎么办**(Ctrl+C / 关机 / 进程被杀): **库不会毁**, 把同一条命令再跑一遍会接着补,
> 补完库里的内容跟一次跑完的一样。
> (续跑那次的汇总里, 数字是**这次新增的**, 所以可能看到 `成员 +0` 之类 —— 那是正常的,
> 不代表没补上。想确认就用 `contacts` / `sessions` 查一下真实条数。)
> **但补齐之前那个库里的数是不全的, 而且查询和 `doctor` 都看不出来** —— 查询照常出数据、
> 不报任何警告, `doctor` 也只查库结构版本、不查数据全不全。所以断过的库别急着下结论,
> 先把 `ingest` 重跑一遍。

- 或者**只导你关心的那几个群/好友** —— 用 `capture` 圈定。

**顺序不能反**: `capture` 要往库里写, 所以得**先有库**(就是上面第二步 `--no-messages` 建的那个),
再圈定, 最后导消息:

```
.\msgvestige.exe capture add "5795****030@chatroom" --l1-db wx.db
```

圈完它会告诉你影响面:

```
已圈定采集会话「5795****030@chatroom」(账号 a1b2c3d4); 当前采集 1 个会话。
⚠️ 首个圈定 → 从「全采所有会话」切到「只采圈定」, 其余会话今后停采 (确认 conv_id 无误; typo 会致只采不存在会话=几乎全停, 可再 rm 恢复)
(生效: 下次 ingest / --to-l1 watch 从下次 source 变化起只采圈定; **正在跑的 `watch --print` 观察用启动快照、需重启**。停采 `capture rm …`; 清空=全采)
```

**注意这个语义**: 一旦圈了第一个, 就从「全采」变成「只采圈中的」。会话 id 打错的话
= 只采一个不存在的会话 = 几乎什么都不采。用 `capture list` 核一遍再导:

```
.\msgvestige.exe capture list --l1-db wx.db
```

```
采集清单 (账号 a1b2c3d4, 共 1 个 → ingest/watch 只采这些会话):
5795****030@chatroom
```

想恢复全采: `capture rm` 加上会话 id, 把圈的都删掉, 清空即恢复。
确认无误后再跑上面那条 `ingest --all`, 就只导圈定的这些了。

导完之后查某个会话的消息:

```
.\msgvestige.exe messages "5795****030@chatroom" --l1-db wx.db --mode cold -n 20
```

会话 id 从上面 `sessions` 的输出里抄。

**注意**:库里没导消息时, 这条命令**不报错**,只是返回 0 条:

```
5795****030@chatroom 最近 0 条:
```

看到「最近 0 条」先想想是不是还没导消息, 而不是以为坏了。

## 卡住了怎么办

### 「没找到微信数据目录」

```json
{
  "_error": "BAD_REQUEST",
  "_hint": "没找到微信数据目录 — 用 --wechat-data-dir 指向 xwechat_files (如 F:\\xwechat_files)"
}
```

它默认找 `我的文档\xwechat_files`。你如果把微信数据存在别的盘, 就得手动指:

```
.\msgvestige.exe auth --scan --wechat-data-dir "X:\xwechat_files"
```

**怎么找这个目录**:微信里「设置 → 通用 → 文件管理」能看到当前存储路径,
那个路径下应该有个 `xwechat_files` 文件夹。

**判据: 查询类和建库类命令, 只要要去读微信的库就得带。** 包括 ——
- `doctor` / `auth` / `ingest` / `watch`

- **任何走 `--mode hot` 的查询** —— 注意 `sessions` 和 `messages` **默认就是 hot**
- `messages` 带 `--wxid` 时(它会去微信库补最新消息)

只有**明确写了 `--mode cold` 查自己那个库**时才不用带 —— 那时候确实不碰微信了。

> **媒体导出那几条是例外, 它们不认这个参数** —— `decrypt-images` / `export-videos` /
> `export-voices` / `decrypt-emoji` / `media-ingest` 给了 `--wechat-data-dir` 会直接报
> `unexpected argument`。它们要你**直接指到库文件**: `--message-db` / `--media-db` /
> `--hardlink-db` / `--emoticon-db` / `--account-dir`, 各自 `--help` 里写着。
>
> ⚠️ **而微信那些库是加密的** —— 直接指过去会报「库是加密的? 加 `--cipher native`…」。
> 所以这几条命令还要再加两个参数:
> ```
> --cipher native --wxid wxid_你的号
> ```
> 加上就能直读加密库, 不用先解密。(密钥用第一步缓存好的那个, 不会再去碰微信。)

### 「检测到 N 个账号」

```json
{
  "_error": "ACCOUNT_AMBIGUOUS",
  "_hint": "检测到 3 个账号 [\"wxid#b2c3d4e5\", \"wxid#c3d4e5f6\", \"wxid#a1b2c3d4\"] — 用 --wxid 指定一个"
}
```

你这台机器上登录过多个微信号, 得说清楚要哪个:

```
.\msgvestige.exe auth --scan --wechat-data-dir "X:\xwechat_files" --wxid wxid_你的号
```

**怎么知道自己的 wxid**: 微信里「我 → 个人信息」能看到微信号。
或者直接去 `xwechat_files` 目录下看有哪些 `wxid_` 开头的文件夹。

> ⚠️ **打错了不会被拦**: `doctor` 不校验这个号存不存在, 你随便填一个它也报「环境就绪」。
> 以 `xwechat_files` 目录下的文件夹名为准最稳妥。

提示里那个 `wxid#b2c3d4e5` 是**打码后的**, 不是真 id。

> ⚠️ **只有报错提示里的账号是打码的。查询结果里的账号是明文** —— 比如 `money` 会打出转账
> 对方的完整 wxid, `friend-requests` 会打出申请人的。这是设计如此(业务表就存明文),
> 不是漏洞。**截图或者贴输出给别人之前自己看一眼。**

### 「实时查需 --wxid」

```json
{
  "_error": "BAD_REQUEST",
  "_hint": "实时查 (--mode=hot, 或 auto 无 --l1-db) 需 --wxid; 要冷查改 --mode=cold --l1-db <L1 库>"
}
```

两种情况都会报这个, **第二种更常见**:

1. **没带 `--l1-db`** —— 它以为你要读实时微信库, 那条路要账号信息。
2. **带了 `--l1-db`, 但没写 `--mode cold`** —— 而你敲的又是 `sessions` 或 `messages`。
   这两条命令的默认是 `hot`(实时), 不是 `auto`。带了库也照样去读实时的。

两种都是同一个解法, 把两个参数都补上:

```
.\msgvestige.exe sessions --l1-db wx.db --mode cold -n 3
```

### 翻页翻着翻着报 `INVALID_CURSOR`

```json
{ "_error": "INVALID_CURSOR",
  "_hint": "游标失效 (账号/过滤/版本不符或格式坏) —— 去掉 --cursor 从头翻" }
```

多半是**翻到一半改了过滤条件**(比如加了个关键词), 或者换了库。游标是跟「哪个库 + 什么过滤条件」
绑死的, 条件一变就作废。按提示去掉 `--cursor` 从头翻就行。(只改 `-n` 条数不受影响。)

### 「库正被别的程序占用」

```json
{ "_error": "BAD_REQUEST",
  "_hint": "--l1-db …\wx.db 打不开: **库正被别的程序占用** … **库本身没问题**, 等它结束或关掉那个程序再试" }
```

**库没坏, 别删。** 多半是这几种:
- 另一个 `msgvestige` 还在跑(比如后台的 `watch`, 或者上一次 `ingest` 没退干净)
- 你用别的数据库工具打开着这个文件

等那个程序结束、或者关掉它, 再跑一次就好。

> 跟这条容易混的是「**不是有效 sqlite 库 (非数据库 / 已损坏)**」—— 那条才是文件真有问题
> (指错文件了, 或者文件损坏)。两条提示不一样, 按提示走就行。

### 微信开着但取不到密钥

多账号的机器上最常见的原因是: **`--wxid` 指的号不是当前登录的那个**。
工具会明说这一点:

```
内存扫 key 失败 (目标账号正登录运行且解锁了? 多账号确认 --wxid 指当前登录那个) …
```

换成当前登录的那个号再试。密钥取过一次就缓存了, 之后切回来查别的号的库不受影响。

### auth 报找不到微信进程 / 扫不到

`--scan` 需要**微信正开着并且已登录**。检查:
1. 微信开着吗?最小化到托盘也算开着
2. 是不是登录了别的号?`--wxid` 指的那个号得是**当前登录的那个**
3. 实在不行, 去掉 `--scan` 用默认方式(会重启微信让你重新扫码, 更慢但更稳)

### 查询很慢

先分清是哪一种慢, 两种的解法完全不同。

**第一种: `messages` 查之前会去微信库补新消息。**
只有 `messages` 这一条命令有这个行为, 而且**只在你给了 `--wxid` 的时候**才发生 ——
它会先把这个会话的新消息增量采进你的库, 代价是这一步要时间。不想等就加 `--no-refresh`:

```
.\msgvestige.exe messages "群id" --l1-db wx.db --wxid wxid_你的号 --no-refresh -n 20
```

代价是可能看不到最新几条。

> ⚠️ **给了 `--wxid` 就必须一起给 `--wechat-data-dir`**(数据不在默认位置时)。
> 少给的后果**分两种, 差别很大**:
>
> - **带了 `--mode cold`**: 不报错, 只在开头印一行「注意: 够不着微信库 … 下面读到的是
>   L1 里已有的, **可能不是最新**」, 然后照常给你库里的旧数据(退出码 0)。
> - **没带 `--mode cold`**(`messages` 默认是 hot): **直接失败, 一条数据都不给** ——
>   报 `BAD_REQUEST` 没找到微信数据目录(退出码 2), 或者目录在但没这个账号时报
>   `ACCOUNT_NOT_FOUND`(退出码 4)。
>
> 两个参数都带上就没这些事:
> ```
> .\msgvestige.exe messages "群id" --l1-db wx.db --mode cold --wxid wxid_你的号 --wechat-data-dir "X:\xwechat_files" -n 20
> ```

> ⚠️ **没给 `--wxid` 的话, 加 `--no-refresh` 没有任何效果** —— 本来就不会去补。
> 上面「三步走」里的例子都没带 `--wxid`, 所以那些命令跟这个标志无关。
> `sessions` / `contacts` / `search` / `moments` / `money` 这些**压根没有**这个标志。

**第二种: 库本身就大, 查询自己慢。**
这种加 `--no-refresh` 不管用。能做的是:
- 少要点数据(`-n` 调小)
- 搜索的话先建全文索引(见**底下**「全文搜索」那节), 差别是秒级 vs 毫秒级

### 磁盘空间不够 / 导出到一半失败

导出媒体很吃空间(几万张图片能到几十 GB)。空间不够时那条会算失败, 命令结束打 ⚠️ 或 🛑,
**写坏的半截文件会自动删掉** —— 输出目录里剩下的都是完整的, 不用自己挑。

腾出空间后**重跑同一条命令**即可, 已经导出来的不会重复导。

### 微信没开着

第一步取密钥要从运行中的微信读, 微信没开会说:

```
微信进程未运行 (找不到 Weixin.exe) — 内存提 key 需微信在跑
```

打开微信登录进去再跑一次就行。**只有取密钥这一步需要微信开着** —— 密钥取到之后,
建库和查询都不用再开微信。

### 提示让我跑某个命令, 但那个命令不存在

如果提示里的命令敲了报「找不到」、或者参数对不上, **以 `--help` 为准**:

```
.\msgvestige.exe 命令名 --help
```

(这类提示写错过 —— 有几处曾经指向内部程序名, 已修。再发现就告诉开发。)

### 想看某条命令还能怎么用

```
.\msgvestige.exe 命令名 --help
```

> 把「命令名」换成真的命令, 比如 `messages`。**别写尖括号** —— `<>` 在 PowerShell 和 cmd 里
> 是重定向符号, 原样粘贴会报 `The '<' operator is reserved for future use.` 之类, 跟工具无关。

比如 `.\msgvestige.exe messages --help`。全部命令列表:`.\msgvestige.exe --help`。

## 全文搜索

这大概是最常用的。**两个地方跟别的命令不一样**, 照别的命令的习惯敲会报错:

- 关键词要用 `--query`, **不能直接跟在命令后面**(`search "你好"` 会报 `unexpected argument`)
- 条数用 `--limit`, **不是 `-n`**

```
.\msgvestige.exe search --query "你好" --l1-db wx.db --mode cold --limit 3
```

**首次搜索前建一次索引**, 不建也能搜(自动退化成全表扫), 但慢。
下面这段是在**另一个库**(210 万条聊天消息)上跑的 —— 只导了小表的库里搜不出聊天记录:

```
[search] 提示: 未建全文索引 → 走全表 LIKE 扫描 (大库慢); `search --l1-db … --build` 建索引后 ms 级。
[search] "你好" 命中 3 条 (取前 3, 10126ms):
  [1784938368000] 2085****353@chatroom｜wxid_70be*******422: @某某 你好
```

上面那个耗时是**另一个库**(210 万条聊天消息)上实测的全表扫。**几秒到几十秒**, 差别很大 —— 实测拿到过
4.0 / 4.7 / 10.1 秒, 也拿到过 71 秒和 106 秒(冷缓存首跑 / 后台还在跑别的抢磁盘)。
取决于库有没有被系统缓存住、盘忙不忙 —— 第一次搜慢是正常的, 再搜一次就快了。建索引:

```
.\msgvestige.exe search --l1-db wx.db --build
```

建完再搜是毫秒级:

```
✅ 全文索引已建 (message_fts): 5303 条消息, 3348ms; 增量触发器已建 —— 后续 ingest 新消息自动进索引, 不用再 --build
```

**只需要手动建这一次** —— 之后 `ingest` 进来的新消息会自动进索引, 不用再敲 `--build`。

> **有新消息时会顺带重建一次索引。** 库大的话这一步要几分钟 —— 所以导入完看着卡一下是正常的。
> (**这次没有新消息就不重建**, 直接跳过。所以反复跑 `ingest` 不会反复卡。)
> 实在不常搜, 也可以先 `.\msgvestige.exe live-index clear --l1-db wx.db` 把索引删掉,
> 要搜时再 `--build` 建回来。

代价是**库文件会明显变大**。实测同一个库建索引前 1114 MB、建完 1209 MB, **涨了 95 MB**
—— 而这还只是 5303 条消息。这个索引能搜中文任意子串, 所以吃空间; 消息多的话按比例涨,
建之前先看看盘还剩多少。建索引本身也要时间(5303 条用了 3.3 秒, 几十万条就是几分钟起)。

## 已知做不到的(不是 bug, 是这套办法的边界)

工具里有几处**明知道盖不全**的地方。它们都不会当成错误报出来 —— 有的完全没声音, 有的会另打一行提示
(下面每处都写明是哪种)。写在这儿, 知道了就不会误以为"程序说没有就是真没有"。

### 换过数据库副本, 可能认不出来

> **这一种完全没声音** —— 探针全通过就是"没换过", 不会有任何提示。

`new`(看新消息)、`search --build`(建搜索索引)、常驻的增量采集, 都靠记住"上次读到哪一格"来接着往下读。
判断"这还是原来那个库吗", 靠的是几个便宜的探针 —— 头一行、上次读到那一行、最大行号、已读段行数。

**首尾对得上、中间不一样**的两份副本, 这几个探针**全都通过**。比如你从备份里恢复了一个旧库,
恰好条数一样、首尾也一样, 那中间那段不一样的消息就**永远读不到**。

碰上了怎么办: `new --reset` 从头重扫一遍; 搜索索引用 `search --build --rebuild`。
什么时候需要这么做: 换过微信数据目录、从备份恢复过、或者你发现某个会话的历史看着不对劲。

真库上量过一个相关的数: 6003 张会话表里 **26 张**中间有空洞(一共 38 个空号)。
按表算约 **1/231**, 按消息条数算约 1/53000 —— 这两个数别混, 早先这儿把"按条数"那个比例
错安在"张数"上了, 把这件事说得比实际稀有 200 倍。
这类空洞**已读段行数**那个探针能逮到; 逮不到的是"两份副本各自长了不同的消息、条数还一样"这一种。

### 实时那条路的同一道保险, 什么时候不生效

上面说的是走 L1 那条路。`new --mode hot`(不给 `--l1-db`, 直读微信库)是另一套: 它给**每张聊天表**
留一个记号 —— 记号那一行的时间、以及从头到它为止(含它自己)有多少行。以下几种情况这道保险不生效。

**甲 · 判不出来, 而且没有任何提示**

- 两份副本的记号那一行时间没变、行数也没变多 → 当成同一个库。(行数只在**变多**时才算换过; 变少
  多半是你自己删了消息, 那不该重报。)
- 头一次看这张表, 或者刚 `--reset` 过 → 两项都还没有基准, 这一轮什么都不比, 扫完才立起来。
- 基准已经有了, 但换进来的副本里压根没有记号那一行(比如它行数更少)→ 时间那项哑火, 只剩行数一项。

**乙 · 这一轮没跑 —— 有缺口就会另打一行提示, 没形成缺口时一声不吭**

(注意"有没有声音"取决于**这张表当时的状态**, 不取决于是下面五种成因里的哪一种: 已经立起基准、
记号又跟位置齐平的表, 五种成因随便哪一种发生, 只要这一轮没读到新行就不构成缺口, 也就没有提示。)

这一轮这张表没扫全, 记号就停在原地不往前走, 它和你实际读到的位置之间那一段就没有保险。没扫全有五种成因:

| 成因 | `--format json` 里看哪个 |
|---|---|
| 游标读到一半被打断(微信开着正在写, 真库上**最常见**) | `scan_truncated_tables` |
| 表里有整行读不出来的(不是只有正文解不开) | `scan_dropped` |
| 整张表这一轮打不开(已知坏分片 / open、prepare、query 失败) | `scan_degraded_tables` |
| 这一轮建不起定位表 —— 口径比字面宽: 分片目录读不了 / 分片打不开 / Name2Id 读不出 / 表列不出 / 行级解码失败 / **有聊天表在 Name2Id 里查不到会话名**(表还在、分片也好好的, 只是这一轮排不进计划) | `scan_build_degraded_shards` |
| 分片文件或这张聊天表这一轮不在了(被删 / 移走) | **没有对应字段** —— 定位表里被静默剪掉, 上面几个 `scan_*` 一个都不涨。但**缺口本身照样计进 `guard_lagging_tables`**(同一份 json 里), 也照样打提示行 |

还有一个字段跟这张表**同门进出, 但它不是"没扫全"的成因**: `scan_content_failed` = 这一行读得出来、
只是正文解不开。这种行**整条跳过, 不会报给你**; 同一张表更靠后的行照常报, 位置就越过了它 —— 之后
就算正文恢复了, 它也不再算"新的", 不重扫就永远看不见。

**多数情况下这一条不静默**: 命令跑完会另打一行 `⚠ N 张会话表各有至少一条消息再也报不出来了`,
把表名和行号一起列出来, 再给一条 `exec` **命令模板**(账号、分片、表名、行号四处要你自己填;
表名是会话 id 的 md5, 得自己算或者去 `sqlite_master` 里查)。想找回来: `new --reset` 重扫一遍 ——
那时候读得出来就补报出来, 一直读不出来就确实回不来了。

三种情况这行**不打**: ① 解不开的那行正好是本轮该表最靠后的(或者它后面的行没进这一批),
位置没越过它 —— 下一轮还读得到, 不算丢; ② `--format json` 模式不打这行;
③ 这一轮护栏判"这张表像是换了一份副本"把它复位了 —— 复位 = 整表从头重报, 旧那份里丢的行跟
新这份没关系, 标记跟着清掉。**别把这一轮没报当成"好了"**: 同一轮会打另一行"⚠ N 张会话表的水位
被复位", 看到那行就知道是这个原因; 而且要是新这份里那一行照样读不出来, 下一轮位置一越过它,
提示就重新立起来。

`--no-advance` 是**第三种情况, 但它不是"不打"**: 加了它就完全按落盘的水位算 —— 水位里
早先记下的丢失照样打出来, 只有**这一轮预览中新发现的**那些不算进去(因为什么都没写下去)。

它**不影响记号**: 从扫描器看这张表算扫全了, 护栏该比还比。但它**单独就能**把 `partial` 顶成 true,
于是上面那几个字段一起冒出来 —— 五种成因那四个全是 0, 只有 `scan_content_failed` 非 0。
看到这个组合别去五种成因里对号入座, 那是另一回事。

⚠️ 上面这几个字段**只在这一轮真出了降级时才出现**。而缺口是**跨轮挂着的状态**。所以: 看见
"护栏覆盖不全"而那几个字段**全缺、或者全是 0**, 不代表没事 —— 那只可能是**这张表这一轮压根没被扫到**。
"没被扫到"除了被删被移走, 还有一种: 水位文件是从别处搬过来的、跟当前这个库对不上。
(**换 `--wxid` 或者挪微信数据目录不算** —— 水位文件名是按"账号 + 消息目录的绝对路径"算出来的,
换任何一个都会去用另一个水位文件、从头开始, 不会把旧记录带到新库上。这一条早先写错过。)

扫得到的表只要这一轮扫全了, 缺口一般会自己合上 —— 要么正常推进, 要么把记号搬到"你读到的位置之前的
最后一行"。有一种例外: 缺口那一段里一行都不剩了(那几条后来被删光), 记号**搬不动**、`gid` 就一直落后,
但这种情况不会再报(确实没东西漏了)。所以水位文件里看到记号落后, 不等于有缺口。

> **这一节说的两行 ⚠ 提示(护栏覆盖不全、消息再也报不出来了)都只在默认的表格输出里打。**
> 加了 `--format json` 就一行都不打 —— 那边靠 summary 里的 `guard_lagging_tables` /
> `tables_with_lost_rows` 这些计数, 自己判。

**什么时候会打那行 "N 张会话表的护栏覆盖不全"**: 这张表还没立起基准; 或者记号落在了你实际读到的
位置后面, 且要么这一轮没扫全(核不了, 如实报)、要么扫全了而那一段里确实还有行。
**什么时候不打**: 基准已经立起来了、记号又跟位置齐平(没缺口) —— 这种表哪怕这一轮整个消失了也照样
不打, 那才是真正没声音的那一种; 扫全了而那一段已经空了(那几行后来被删光了); 这张表刚被复位
(那算另一行提示 `guard_reset_tables`)。

⚠️ "这一轮一条新的也没报出来"**不等于**不打。缺口和"还没立起基准"都是**存在水位里的状态**, 是上一轮
留下的 —— 这一轮哪怕一条新消息都没有, 照样接着报。这一轮没报出新消息只是不会让缺口**再变大**。

碰上了怎么办: `new --reset` 从头重扫一遍(代价是整表重报一遍)。

### 搜索索引那条路探针更少

> **这一种完全没声音** —— 探针少一个, 该逮的没逮到, 不会有任何提示。(探针**逮到**换库时倒是会在
> 日志里打一行"源表换过了 → 该会话从 0 重抽"; 这里说的是逮不到那种。)

搜索索引(`search --build` / 常驻建索引)为了不拖慢, 只用其中四个探针, **不含**"已读段行数"那一个。
所以上面说的"中间被挖了洞又补回来"那种, 搜索索引这条路盖不住 —— 结果是**搜不到那一条**,
但消息本身在库里, 用 `messages` 查得到, 数据不丢。

### 一次看新消息, 忙的会话会占满名额

> **这一种默认输出里不提, 但 `--format json` 里看得出来**: 实时模式给 `total_new` / `new_shown`;
> 冷查只给 `has_more`, 只说明还有没有下一批、不给条数。
>
> ⚠️ `total_new` **只有这一轮全扫干净时才是确切条数**。有表没扫全(被打断 / 打不开 / 没排进计划)时,
> 那些表的新消息压根没被数进去 —— 这个数会**偏少**, 别拿它当"就剩这么多了"。判断办法: 同一份
> json 里 `partial` 是不是 true、几个 `scan_*` 是不是非 0, 两个一起看。

`new` 一次最多给 N 条(默认 50), 按会话顺序发。有个会话一直在来消息的话, 它会一直占着名额,
安静会话的新消息这一次就轮不上。**数据不会丢** —— 没发出来的下次还在, 只是当时看不到。
想都看到: 把 `-n` 调大; 或者用 `--per-conv N` 先给每个有新消息的会话留 N 条, 剩下的名额再按原来的顺序补
(默认 0 = 不开; **只有实时模式认这个参数**, 走冷查给了大于 0 的值会当场报错)。
`--per-conv` 别开到接近 `-n`: 露面的会话不但不会变多, **还可能比不开时更少**。
原因是两个顺序不一样: 保底按**会话 id**(wxid / 群号, 不是通讯录里的显示名)排序攒,
不开时按 (分片, 会话 id, 行号) 顺序取 —— 分片在前。
所以会话 id 最靠前的那个会话要是落在靠后的分片里, 不开时它排在后面、名额先给了靠前分片里的一堆会话;
`--per-conv` 开到满额时它却排第一, 只要它这一轮的新消息够多就能把名额全占走。
实测(把这两个函数原样搬出来跑): 一个会话在 `message_5.db` 有 200 条新的、另外 20 个在 `message_0.db`
各 10 条 —— 不开露 5 个会话, `--per-conv 50` 只露 1 个。

不是每次都这样: 那个会话本轮新消息不够多时反而可能多露一个(实测 6 > 5), 靠前分片本轮新消息总数
不到 `-n` 时它不开也照样进得来。但**"开大了一定更好"是错的**, 所以: **留几条就写几条, 别顶着 `-n` 写。**

(早先这里写的是"用 `--conv` 单独看某个会话" —— `new` 没有这个参数, 是写错了。要单看某个会话用 `messages <会话>`。)

## 还能做什么

工具有 **59 个子命令**(`--help` 列出 60 行, 其中一行是内置的 `help`)。
上面用到了 11 个: doctor / auth / ingest / sessions / contacts / capture / messages /
search / live-index / wipe / logs。其余大类:

| 想做的事 | 命令 |
|---|---|
| 全文搜索聊天记录 | `search` —— 见上一节 |
| 导出到 JSON 文件 | `export` |
| 导出图片 / 视频 / 语音 | `decrypt-images` / `export-videos` / `export-voices` |
| 朋友圈 | `moments` |
| 导朋友圈图片视频 | `export-sns-media` —— **看「落 N」那个数字, 别看对勾**(见下) |
| 转账红包 | `money` |
| 起个本地服务给网页/程序调 | `serve` |
| 给 AI 助手直接问数据 | `mcp` |

> **导出命令怎么看结果**(`decrypt-images` / `export-videos` / `export-voices` /
> `decrypt-emoji` / `export-sns-media` / `media-ingest`):
> - ✅ = 真有东西导出来了, 退出码 0
> - ⚠️ = 导出了一部分但有失败, **退出码非 0**
> - 🛑 = 一个都没导出来, **退出码非 0**
>
> 有个例外看着像失败其实不是: **扫到很多条、但「已清理(盘上无)」也很多** —— 那是微信
> 自己把旧文件删了, 数据库里还留着记录。这种打 ✅ 退出码 0, 重试也没用。
>
> `decrypt-emoji` 和 `export-sns-media` 的失败原因还全塌成一句「URL失效或解不出」——
> 分不清是链接过期(常见, 老动态的 CDN 链接会失效)还是环境没配好。
> 排查按各自的依赖来, **它们要的东西不一样**:
> - `export-sns-media` 要 **Node + wasm** → 用完整版包(自带), 精简版做不了
> - `decrypt-emoji` **谁都不要**(只联网下载), 全失败基本就是链接过期
> - `export-voices` 导出本身**不要 ffmpeg**, 只有 `--mp3` 那一步要

每个都能 `--help` 看用法。

## 换新版本

拿到新包直接覆盖装:

1. 删掉旧的解压目录(或解压到新目录也行)
2. 解压新包
3. **拿旧库跑一次体检** —— 这一步不能省, 原因见下:

```
.\msgvestige.exe doctor --l1-db wx.db --wechat-data-dir "X:\xwechat_files" --wxid wxid_你的号
```

> 参数要带全 —— 只写 `--l1-db` 的话, 微信数据目录那项会红, 最后一行就变成「环境未就绪」,
> **可你的库其实是好的**。这条命令的总评说的是**整个环境**, 不是「你的库行不行」。
> **看 `L1 库 schema` 那一行的图标就够了**, 别看最后那行总评。

**密钥缓存不用动** —— `%LOCALAPPDATA%\msgvestige\` 照旧, 不用重新 auth。

**但你的 `wx.db` 要看这一版有没有改过库结构。** 改过的话旧库就用不了了, 而且是**每一条查询都用不了**,
不是只有导入用不了。上面那条体检会直接告诉你:

```
  ✅ L1 库 schema  版本 3, 跟本程序一致 — 可以接着用
```

要是这样, 那就是这一版改了库结构:

```
  🛑 L1 库 schema  版本 2, 本程序要 3 — **这个库用不了了**: 每条查询都会报 SCHEMA_MISMATCH。
                   只能删掉它重跑一次 ingest 全量重建 (密钥缓存不受影响, 不用重新 auth)
```

这时候只能删掉 `wx.db` 重跑一遍 `ingest`。**导过聊天记录的话这就是几小时重来** ——
所以换版本前先拿这条命令确认一下, 别等导到一半才发现。

还有第三种结局, **别把它当成通过**:

```
  🛑 L1 库 schema  找不到: …\wx.db — 这一项**没查成**(不是查过了没问题); 路径写对了吗?
```

还有几种也会红, 措辞各不相同但意思一样 —— **这一项没验成**, 不是「验过了没问题」:

| 你指到的东西 | 它会说 |
|---|---|
| 路径打错 | 找不到: … |
| 一个目录 | 是个目录, 不是文件: … |
| 不是数据库的文件 | 不是能用的 sqlite 库 (文件损坏 / 根本不是数据库) |
| **更老版本建的库**(连版本号都没有) | 有数据但读不到版本号 — 是旧版本建的库…只能删掉重建 |

最后一种也是「这一版改了库结构」的一种, 同样只能重建。
**唯一的 ⚠️ 是空库**(「还没 ingest 过」)—— 那不算问题, 跑一次 `ingest` 就好。

> 目前为止库结构升过两次。升级不做自动迁移, 就是直说让你重建。
> **注意**: 不带 `--l1-db` 的 `doctor` **查不出这件事** —— 它只看环境不看库, 会报「环境就绪」,
> 然后你在第一条查询上撞墙。所以换版本后一定要带上 `--l1-db`。

## 它把东西放在哪 / 怎么卸干净

除了你解压的那个目录和你自己指定的库文件, 它在这些地方留东西:

| 路径 | 是什么 |
|---|---|
| `%LOCALAPPDATA%\msgvestige\cache\keys.enc` | 缓存的微信密钥(加密存的) |
| `%LOCALAPPDATA%\msgvestige\cache\image_keys.enc` | 缓存的图片密钥 |
| `%LOCALAPPDATA%\msgvestige\logs\` | 日志(`logs bundle` 收集的就是这里) |
| `%TEMP%\wxquery_locator_*.json` | 查询用的定位表, **每个 1.6 MB 左右**, 从微信库派生 |
| `%TEMP%\msgvestige_new_wm2_*.txt` | `new` 命令记的「上次看到哪儿了」 |
| `%TEMP%\msgvestige_new_hotwm_*.json` | 同上, 实时查那条路的 |
| `%TEMP%\wxwatch-<数字>\` | **`watch` 的临时库, 会很大**, 见下 |
| `…\cache\keys.enc.lock` | 0 字节的锁文件, `wipe` 不删它 |

**不写**注册表、不装系统服务、不常驻后台。

> ⚠️ **`watch` 这条要留意**: 它默认是「观察」模式(不带 `--to-l1`), 会在
> `%TEMP%\wxwatch-<进程号>\` 建一个临时库放读到的消息 —— **里面是解密后的明文聊天记录**,
> 而且**会很大**(实测跑 8 秒就留下 1.6 GB / 29 万条)。
> 正常结束会自己清掉, 但 `watch` 默认一直跑、只能 Ctrl-C 停 —— **这么停就会留下**。
> 下面的 `wipe` 会删它。

### 卸载

有个现成命令, 比手动删靠谱(手动很容易漏掉 `%TEMP%` 里那几个):

```
.\msgvestige.exe wipe
```

**默认只是预演, 不会真删** —— 先给你看要删什么:

```
预演 — 以下会被删 (加 --yes 才真删; base=C:\Users\…\AppData\Local\msgvestige):
  ● key 缓存 (删了要重新 auth)  …\cache\keys.enc
  ● 图片 key 缓存 (删了要重新扫)  …\cache\image_keys.enc
  ● 日志目录  …\logs
  ● 临时文件 (水位/定位)  …\Temp\wxquery_locator_backup.json
  ● 临时文件 (水位/定位)  …\Temp\wxquery_locator_wxid_xxx.json
  ● 临时文件 (水位/定位)  …\Temp\msgvestige_new_wm2_3b40f619….txt
  ● 临时文件 (水位/定位)  …\Temp\msgvestige_new_wm2_777880eb….txt
共 7 项存在。加 --yes 真删 (含 key 缓存 → 之后要重新 auth; 想保留加 --keep-keys)。
```

确认没问题再加 `--yes` 真删。想留着密钥(以后还要用)就加 `--keep-keys`。

**`wipe` 不会碰你的 `wx.db` 和导出的文件** —— 那些是你指定的路径, 得自己删。
所以卸载是三步: `wipe --yes` → 删解压目录 → 删你自己的 `wx.db` 和导出目录。
`wipe` 删的是**文件**, 空目录会留下(实测跑完 `%LOCALAPPDATA%\msgvestige\` 还在);
auth 过的话还会剩一个 0 字节的 `cache\keys.enc.lock`。介意就手动把
`%LOCALAPPDATA%\msgvestige\` 整个删掉, 一了百了。

## 杀软报毒怎么办

它要读微信进程的内存来取密钥(这是取密钥唯一的办法), 这个行为杀软可能拦。
**拦了就是不能跑**, 不是跑得慢。把**解压目录**加进信任区:

- **Windows Defender**: 设置 → 隐私和安全性 → Windows 安全中心 → 病毒和威胁防护 → 排除项 → 添加排除项 → 文件夹
- **360**: 主界面 → 设置 → 信任与拦截 → 文件信任 → 添加目录
- **火绒**: 设置 → 信任区 → 添加文件夹

三个都填**同一个路径**: 你解压 `msgvestige.exe` 的那个文件夹。
